## 一、91吃瓜（www.91cg1.com）

### 1. 站点形状

Typecho + Mirages 主题，全 HTML，没有 JSON 接口：

| 用途 | 路径 |

| 分类 | `/category/{slug}/`、`/category/{slug}/2/`（**分类页翻页是 `/2/`，不是 `/page/2/`**） |

分类 22 个（今日吃瓜 / 必吃大瓜 / 最高点击 / 91探花 / 海角乱伦 / 自拍偷拍 / 实时偷拍 / 明星黑料 / 明星AI /

投稿求瓜 / 91周榜 / 91月榜）。

### 2. 三个解析要点

1. **卡片**：`<a href="/archives/{pid}/">` 开头的一块，内含 `loadBannerDirect('封面')`、
   `<h2 class="post-card-title">标题`、`<span>分类, 分类</span>`、`datePublished" content="…"`。
   ★ 搜索页的链接是**绝对 URL**（`https://www.91cg1.com/archives/…`），只按相对路径切会一条都抓不到。
2. **图片**：正文里的 `<img src>` 全是懒加载占位图 `/usr/plugins/tbxw/zw.png`，
   真图在 **`data-xkrkllgl="https://pic.hdhwqx.cn/…jpeg"`**，直连 200 + `image/jpeg`，不需要 Referer。
3. **视频**：帖子页内嵌 DPlayer 配置：
   `"video":{"url":"https://op.udhhzr.cn/videos5/{hash}/{hash}.m3u8?auth_key=…&v=3&time=0&project_id=tj015&pv=1","type":"hls"}`
   JSON 里的 `\/` 要还原成 `/`。实测清单 `200 + #EXTM3U`，清单内的 AES key 与 `.ts` 分片分别在
   `as.ucjosl.cn` 上、逐条带好自己的 `auth_key`，播放器直接放即可（不需要 Referer）。

### 3. 为什么拆成两个源

每篇帖子都同时有图集和短片（抽样 10 篇：图片 3–53 张、视频 1 段），而 LumeBox 一个源只能属于一个板块：

- `sources/photo/91cg1.js`（`cg1_photo`，漫画板块「美图」分组）→ 只出图片；
- `sources/video/91cg1.js`（`cg1_video`，视频板块）→ 只出短片，帖子没有视频时回落到网页播放器。

两个源共用同一套抓取逻辑（卡片/帖子解析 + 帖子页 10 分钟缓存），只有 `chapters()` / `content()` 不同。

node tools/lume-source-check.mjs sources/video/91cg1.js --keyword 偷拍

  搜索 30 条、`detail` ok、`chapters`「全部 53 张图片」、`content` 53 张图、首图 200 + `image/jpeg`；
- 短片源：同样四个入口，`content` 给 `op.udhhzr.cn` 的 m3u8，探活 `200 + #EXTM3U`（41 KB）；
- `--page 2` 两源都正常（30 条、`hasMore=true`）；分类页翻页 URL 单独验过 `/category/zxcghl/2/` = 200。

## 二、BetaTok（betareel.com）

### 1. 数据链路

```
GET https://betareel.com/api/betatok/feed
→ {ok, manifestUrl: "<R2 预签名 URL>", mediaBase: "/api/betatok/media/",
   mediaQuery: "e=1793095200&t=<token>", expiresAt}
GET <manifestUrl>   → 27 MB / 34466 条的整包 JSON（对象本身 gzip 3.7 MB）
```

清单结构：`{version, generatedAt, count, channels[84], items:[{id, type, videoKey, posterKey, batchId, author,
authorUid, description, tags[], channels[], timestamp, publishedAt, views, locked, price, unlockType}], creators, stats, keys}`。

播放：`/api/betatok/media/{videoKey}?{mediaQuery}` → **302 到 R2 预签名 mp4**（实测 206、`video/mp4`、
单个文件 60 MB）；加 `&json=1` 则返回 `{ok:true,url:"<R2 直链>"}`。
封面：同一代理路径换成 `{posterKey}` → 200 `image/jpeg`。

### 2. 沙箱里怎么读 27 MB 清单

整包解压 27.7 MB，`JSON.parse` 必然撞 64 MB 堆上限。但对象是 gzip 存的、**支持 Range**：

- `Range: bytes=0-65535` → 解出 551 KB 文本 ≈ 680 条；
- 用 `},{"id":"` 切条（清单里每条都以 `{"id":"` 开头、字段全是标量/字符串数组，没有嵌套对象），
  只 `JSON.parse` 需要的那几条；
- 页面需要多少条就按 `need × 200` 字节估窗口，最大 1 MB 压缩（≈8.6 MB 文本 ≈ 1 万条）；
- ≤128 KB 的窗口进 `LumeSource.fs` 缓存（5 分钟），详情/选集/播放复用同一段文本。

Dart 侧单独验过：`HttpClient` 拿 `Range` + `Content-Encoding: gzip` 的部分响应是**正常解压**的
（206、`bodyBytes=551068`、开头就是合法 JSON），不会因为 gzip 流被截断而抛错 —— 这是本源敢用窗口的前提。

### 3. 实测

```
node tools/lume-source-check.mjs sources/video/betareel.js
```

`home` / `filters`(84 频道) / `categories` / `list` / `detail` / `chapters` / `content` 全 ok：

- 窗口第一次 2.0 s，之后全部 1 ms（走 fs 缓存）；
- `content` 给 `https://betareel.com/api/betatok/media/content/…mp4?e=…&t=…`，
  用 `Range: bytes=0-262143` 手工复验：**206 + `video/mp4` + `content-range: bytes 0-262143/60540624`**。

**唯一的「失败」是工具误报**：`tools/lume-source-check.mjs` 验播放会把整段 mp4 拉完，
60 MB 必然撞它自己 20 s 的超时。这不是源的问题（同一 URL 的 302/206 都已验证），已在 README 限制里写明。

### 4. 限制

- 搜索与频道筛选只作用于**当前窗口**（上限 ≈2.8 千条），没有全站搜索（站点本身也没有搜索接口）；
- `locked:true` 的付费片（PPV，钻石价）不列，`content()` 也拒绝代下单；
- 清单 URL 是 9000 s 预签名，脚本按 `expiresAt` 提前换票，401/过期会自动重新引导。
